# One actual repair trial

This trial has not been run. Its purpose is to show a person responding to ProofLoop's displayed request and receiving a result from fresh observations. The existing online videos test perception and chronological states; their actions happened before our requests.

Use the current production workbench at `http://127.0.0.1:8790/`, one fork, one spoon and the divided paper. Fix the camera, lighting, requirements and perception mode before starting. Review **fork LEFT / spoon RIGHT**, the regions and the unique-target assumption. The new concept-mask and gripper experiments remain separate from this trial.

1. Screen-record the app before the first inspection. Keep all attempted pairs and model outcomes.
2. Put the fork in RIGHT and the spoon in RIGHT, separated, wholly inside the region and away from the divider. Use **New inspection → Use camera → Capture two views**. Keep hands out of both captured views and submit within the camera freshness window.
3. If the actual result is FAIL, read the displayed repair request. Choose **Start repair before moving the fork**. An UNKNOWN result requires the requested evidence instead; it is not a diagnosed wrong placement.
4. Open **Use camera** again so the preview shows the operator's response. Move the fork to LEFT, leaving the spoon in RIGHT. Remove the hand, then capture two new views.
5. Choose **Verify correction**. Preserve PASS, FAIL, UNKNOWN or ERROR exactly as returned. Do not reuse the initial images.
6. If PASS, show the before/request/after record and **Evidence log → Linked recovery record → Check local evidence**. Replay consistency and supported final placement are separate claims.
7. Record actual pair count, request count, cost uncertainty, time from request to result and anything confusing. Keep failures. One operator's observation does not establish customer demand or time savings.

The app captures two views two seconds apart. With two objects, default concept mode uses at most four SAM calls per pair; guided production mode adds one Spark call per pair. Fix and disclose the actual mode. Predeclare one initial pair, one correction pair and, only when explicitly requested by UNKNOWN, at most two bounded follow-up pairs. Do not keep spending until a flattering run appears.

Success for this single demo requires an actual current FAIL, a repair request before the visible move, new distinct observations, supported final placement and a consistently replayed linked record. A continuous screen recording can show a person following the request. The software still checks visual state and evidence lineage; keep `physical_action_execution_verified: false` and make no robot-motion, safety or full-procedure claim.

For the three-minute submission, lead with the problem and this observed loop. Then show one honestly labeled uncertainty example, the evidence record, Meta's actual model roles, one measured failure and the public repository. Shortened waiting should carry its real elapsed time. Until this trial supplies results, the [existing cached-replay script](DEMO-SCRIPT.md) remains a diagnostic demonstration.
