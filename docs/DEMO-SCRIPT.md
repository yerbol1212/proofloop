# Three-minute ProofLoop demo

This script demonstrates the current product and actual recorded Meta results. It does not require new phone footage. Record the normal workbench with the existing private, licensed Video lab runs available. Keep **Recorded** provenance and the Spark baseline visible. Do not present a replay as a live robot following a request.

## Before recording

- Build the frontend and start the local Python server as described in [INTERACTIVE.md](INTERACTIVE.md). Open the normal workbench and confirm the fixed future-pair and candy runs appear in Video lab. Opening them makes no model calls.
- Prepare the windows needed for Task, Video lab, Workflow, and the public repository. Do not activate a changed contract merely for the recording if a current run or receipt needs to remain intact; an unapproved draft is sufficient to demonstrate the review boundary.
- Use a visible caption with online imagery: **“External ALOHA / LeRobot recordings. Authored placement labels. Recorded-frame analysis.”** Include the dataset credits and pinned source links in the submission description.
- If showing any injected-client UI or test case, label that segment **“Authored software fixture — no model inference.”** The main recorded-results walkthrough below uses actual saved Meta responses.

## 0:00–0:20 — State the concrete problem

**Screen:** Inspection or Video lab with an UNKNOWN result and its requested evidence.

**Narration:** “A visual assistant can describe a scene, but a workflow needs to know whether a specific preparation step is supported—and what evidence is missing. ProofLoop turns reviewed placement requirements into pass, fail or unknown, then asks for the particular view it needs. A proposed action never counts as proof that it happened.”

## 0:20–0:45 — Make the requirement reviewable

**Screen:** Task → **Use coffee video preset** → unique-target confirmation → **Review authored coffee checks**. Show the authored origin, single glass, DISPENSE/STAGING IDs, guided-v2 method and unapproved state. Avoid activating unless the demonstration deliberately starts a new reviewed task.

**Narration:** “Here the requirement is one declared unique glass in DISPENSE. This preset is authored; custom requirements use Muse Spark to draft checks. Neither becomes active without exact review. Changing a target, region or method invalidates earlier evidence. The same editor supports one to six targets and meaningful region names.”

## 0:45–1:30 — Show UNKNOWN becoming a specific, finite request

**Screen:** Video lab → **Specific evidence requests — fixed future pairs**. Show episode 000000's initial pair, first future pair and second future pair. Keep source timestamps, typed view gaps and the two-follow-up count visible. Briefly show the terminal episode.

**Narration:** “These are real, licensed robot recordings. Every pair and label was fixed before inference. The first guided result cannot support full glass visibility, so the request identifies the object and views to improve. The next scheduled pair still has ambiguous identity; the request changes accordingly. Only the second permitted follow-up supports PASS. Both later images must be new and strictly later—there is no searching until a favorable answer appears. This terminal case has no admissible future pair, so ProofLoop stops with UNKNOWN. These recorded movements were not caused by our requests.”

## 1:30–2:00 — Keep the model comparison honest

**Screen:** Fixed-pair scorecards, then **New task transfer — candy collection**. Show the early UNKNOWN and final PASS; preserve the baseline and source attribution.

**Narration:** “On all six fixed coffee pairs, guided Spark plus SAM matched four labels; Spark alone matched six. The contribution is explicit evidence control, not a claimed accuracy advantage. We also tested a different candy task: both matched two out of two, UNKNOWN then PASS. The early packet-area anchors were rejected by the unchanged SAM confidence gate. That is not independent proof of correct semantic identity.”

## 2:00–2:30 — Show the boundary before continuation

**Screen:** Workflow → **Placement preparation checkpoint**. With recorded-only or expired evidence, show the blocked current-preparation gate and disabled continuation. If a genuine fresh supported inspection is available, **Check preparation evidence** can replay it; otherwise leave it blocked. Do not upload historical frames as declared current captures to obtain a green gate.

**Narration:** “A recorded PASS cannot unlock a current preparation checkpoint. The exact reviewed task needs fresh supported placement and replayed source evidence. Only then can an operator record a separate decision to continue. That record is a declaration, not observed dispensing or proof of a whole procedure. Historical, uncertain, expired or altered evidence blocks the gate. Fresh physical operation following a displayed request remains our next validation step.”

## 2:30–3:00 — Identify the new work and reproduction path

**Screen:** Evidence log or the review record, then repository README and [REPRODUCING.md](REPRODUCING.md). Show the no-API default plan command or its saved output.

**Narration:** “During the hackathon we built the task compiler, Meta adapters, three-state checker, bounded repair and evidence-request policy, workbench, replay records and preparation gate. Muse Spark and SAM are Meta's pretrained models; ALOHA and LeRobot supplied the external recordings. The public clone can acquire one pinned licensed clip and prepare four frames without API calls. Raw credentials and responses stay private. The next tests are independent identity, wider procedures and a current operator completing the physical loop.”
